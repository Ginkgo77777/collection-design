# 代表性案例: 思源黑体完整生命周期(示例)

## 单条资产登记（填写骨架）

| 字段 | 记录 |
| --- | --- |
| 稳定 ID / 名称 | `AST-2026-0001` / 思源黑体（示例） |
| 作者 / 来源 | 实际作者、官方下载页及所用 Release / Commit |
| 授权依据 | 所用版本的 LICENSE 固定链接或小型授权文件，注明署名、修改、再分发条件 |
| 文件位置 / 版本 | 实际字体文件路径、版本与对应元数据路径；不必复制字体本体到考核仓库 |
| 分类 / 标签 / 状态 | 按 [命名规则](../naming-and-tags.md) 填写，状态及变更日期与下表一致 |
| 使用位置 | task4 的实际 Figma 文本样式 / 节点链接、项目版本；代码使用时填文件 / Commit |
| 维护者 / 更新记录 | 代号、日期、操作与原因；未发生更新和归档如实注明 |

下面演示记录方式，实际字体版本与授权须按下载来源核对；不能仅凭文件名或字体名称完成授权判断。返回 [提交索引](../README.md)。

## 案例说明

这个案例的典型之处在于: 资产在 task2 时"只存了文件", 收编时才补全来源与授权, 因此走了完整的 Inbox → Approved 流程。
教训: **收集时顺手记录来源, 比事后溯源成本低得多**。
